## A. Spotify catalogue search

**A0. The search operation changed under us (found 2026-11-10)** — corrected
  again 2026-11-10 evening
- **Correction.** The earlier reading of the live bundles was too strong. The
  per-tab family (`searchTracks`, `searchAlbums`, `searchArtists`,
  `searchPlaylists`) is still shipped, with the hashes the table already had;
  `browseAll`, `browsePage` and `lookupChildEntities` are too. Spotify ships
  **both** families: the per-tab operations on `searchTerm` for the results and
  "see all" pages, and the assisted-curation operations on `term` for the
  search page's sections. The table now carries both.
- **The actual fault** (reported: "Spotify search yields no result"): the
  `assistedCurationSearch` request was sent with a *subset* of the operation's
  variables — `term`, `limit`, `numberOfTopResults`. The web player also sends
  `offset` and `includeEpisodeContentRatingsV2` at every one of its call sites.
  A persisted query asked without one of its variables is refused as a whole
  request: HTTP 200, an `errors` array, no `searchV2`, and a results list that
  looks like an empty catalogue. Read off the player's own bundles, not guessed.
- **Fix.** SpotifySearch sends each operation's complete variable set and walks
  three ways of asking until one answers with a search section:
  `assistedCurationSearch` (`term`), `searchDesktop` (`searchTerm`, added to
  the table with `eef7cc54...`), then the per-tab family. The top results are
  read for every kind — a section build answers with everything there — and the
  operation that answered is logged, so the next build's change is visible.
- **Flow's half of the same fault.** `queryArtistOverview` — which "Fans also
  like" reads, and which is what Flow falls back to when Spotify will not make
  a station — also has a variable this app was not sending,
  `includeMusicVideoPreviews`. Fixed, with `searchArtists` as a fallback for the
  artist lookup itself.
- The answer keeps the old shape: `data.searchV2.tracksV2.items[].item.data`,
  `.artists.items[].data`, `.albumsV2.items[].data`, and
  `.topResultsV2.itemsV2[].item.data` (playlists now come from there).
- Also stale in the bundled table and now corrected from the live build:
  `getAlbum` → `0b6ce351…`, `queryArtistOverview` → `eafb1620…`.
- Added: `searchSuggestions` (`f244254b…`) for the typeahead, and
  `getArtistNameAndTracks` for Spotify's own artist expansion.
- The operation table is still refreshed from the player's own bundles at
  start, so this is the fallback, not the source.

**A1. Search source "Spotify" does not exist**
- Symptom: the Search tab only offers YouTube and Library.
- Cause: `SearchSource` had no `SPOTIFY`; nothing called `SpotifySearch`.
- Fix: enum value, source-aware cache key/prefix/session, pipeline branch,
  three-way UI switcher, nav toggle cycle, auto-select on Spotify provider.
- Verify: unit test for source-isolated cache; on-device search shows Spotify
  rows; YouTube cache never leaks into Spotify results and vice versa.

**A2. Filter tabs disagree with the request**
- Symptom: choosing "Videos" then switching to Spotify asks for a tab Spotify
  does not have.
- Cause: filter list was YouTube-shaped.
- Fix: `VIDEOS` resets to `ALL` on Spotify; `PODCASTS` stays the Apple
  directory path.
- Verify: switching sources with each filter pill selected.

**A3. YouTube completions leak into Spotify search**
- Symptom: typeahead suggestions are YouTube's while the results are Spotify's.
- Cause: one suggestion pipeline for every non-Library source.
- Fix: suggestions suppressed in Spotify mode until Spotify's own
  `searchSuggestions` operation is bundled.
- Verify: typing in Spotify mode shows no YouTube media typeahead.
- TODO: bundle `searchSuggestions` + parse `data.searchV2.topResultsV2.itemsV2`.

**A4. Spotify pagination**
- Symptom: no way to reach the second page of a Spotify search.
- Cause: the pipeline only knew YouTube's continuation tokens.
- Fix: `Page.nextOffset`, per-tab paging info, `loadMoreSpotifyResults`.
- Verify: scroll to the end of a Spotify search, next page arrives, no
  duplicate rows.

**A5. Spotify operation hashes can go stale**
- Symptom: an empty Spotify search with a log line nobody reads.
- Cause: a refused persisted-query hash looks exactly like an empty catalogue.
- Fix: classify stale/unknown operation errors, force one operation-table
  refresh, retry once, then report the error instead of "no results".
- Verify: a deliberately wrong hash recovers.

## B. Spotify playlist pages stop after a handful of songs  ← LIVE BUG

**B1. "Daily Mix" / any Spotify playlist loads only the next 8 songs** — CAUSE FOUND, FIXED
- Symptom (user report): opening a full daily mix, or any Spotify playlist,
  loads 8 songs and never loads the next ones.
- Cause 1 (the page stopped early): `parseTrackPage` fell back to
  `content.totalCount ?: rawItems.size` — when Spotify's answer states no
  total, the *page's own size* was read as the *playlist's length*, so the
  paging loop ended after the first short page. Eight songs, and nothing
  after them.
  - Fixed: `TrackPage.total` is nullable. A playlist that states no length is
    paged until Spotify answers with an empty page; a page's size is never a
    playlist's length. `totalCount` is also read from `playlistV2.totalCount`
    and `playlistV2.totalLength`.
- Cause 2 (the queue stopped early): a Spotify page lists its tracks before
  it knows which of them this app can play. Play pressed in that window queued
  only the rows that had already matched — eight songs of a daily mix — and
  nothing was ever appended.
  - Fixed: the page's job is kept (`spotifyPageJobs`), Play and Shuffle wait
    for it (`viewModel.resolvedSpotifySongs`), and the whole page is queued.
- Cause 3 (the request was the wrong one): the track list was read with
  `fetchPlaylist` and the metadata variables. The current web player reads a
  playlist's contents with `fetchPlaylistContents` and
  `{uri, offset, limit, includeEpisodeContentRatingsV2}` — the same persisted
  hash under a different name, but different variables.
  - Fixed: `fetchPlaylistContents` added to the operation table and used.
- Verify: a 50-song daily mix shows all 50, scrolls, and plays through to the
  end without stopping.

**B2. Playlist pages with no tracks**
- Symptom: a Spotify playlist page can show "no tracks" for a playlist that
  has songs.
- Cause: pending.
- Verify: daily mix, a user playlist, and Liked Songs all show their tracks.

## C. Flow in Spotify mode

**C1. Flow shows an empty page**
- Symptom (user report): "FLOW IS NOT REBUILDING, IT JUST SHOWS EMPTY".
- Cause: the only seed sources were `/v1` top-tracks / recently-played /
  featured-playlists, all rate-limited (`429`) for this client → empty seeds
  → empty Flow. The code deliberately refuses to fall back to YouTube seeds,
  so the failure showed as an empty page.
- Fix (in working tree): seeds read the web player's own GraphQL —
  Liked Songs first, then top/recent; signed out uses the home feed's public
  playlist tracks.
- Verify: signed-in and signed-out Flow both build; seeds are non-empty.

**C2. Flow expands through YouTube's radio**
- Symptom: a Spotify mix is padded with YouTube Music radio tracks.
- Cause: `FlowEngine.buildInitialQueue` called `YtMusicRepository.radio(...)`
  directly — no provider awareness.
- Fix (in working tree): `buildInitialQueue` takes a `relatedTracks` expander;
  Spotify passes `SpotifyAlgorithm.more`; YouTube keeps its own radio.
- Verify: no YouTube radio call happens while the provider is Spotify.

**C3. Flow's top-up grows through YouTube's radio**
- Symptom: the list stops growing with Spotify material.
- Cause: `growFlow()` called `YtMusicRepository.radio(...)`.
- Fix (in working tree): `growFlow` uses `SpotifyAlgorithm.more` on Spotify.
- Verify: growing a Spotify Flow adds Spotify-picked songs.

## D. Autoplay in Spotify mode

**D1. Autoplay shows the listener's YouTube liked songs**
- Symptom (user report): "AUTOPLAY IS JUST SHOWING MY YOUTUBE LIKED SONGS".
- Cause: the only Spotify source for autoplay was the seed pool — Spotify's
  Liked Songs, matched to YouTube audio, which is the same recordings the
  listener liked on YouTube.
- Fix (in working tree): every autoplay batch asks Spotify's own algorithm
  first — the station Spotify would start for the playing track, then the
  artists Spotify puts beside that track's artist.
- Verify: autoplay on a Spotify session offers songs that are not the liked
  list; the liked list is only a last resort.

**D2. "Start radio" used YouTube's related list**
- Cause: the overflow menu's radio asked YouTube for related tracks.
- Fix (in working tree): `station = true` → Spotify's `inspiredby-mix`
  station for the current track.
- Verify: start radio on a Spotify-matched track plays Spotify's station.

**D3. Android Auto "start station" is not a station**
- Cause: `PlaybackService.startStationFromSession` called autoplay without
  `station = true`.
- Fix (in working tree): it asks for a station.
- Verify: Android Auto station on a Spotify session starts a Spotify station.

**D4. Player's "more like this" is YouTube's**
- Cause: `AndroidPlayerHost.queueSuggestions(SIMILAR)` called
  `YtMusicRepository.radio` directly.
- Fix (in working tree): provider-aware — Spotify's algorithm on Spotify.
- Verify: the queue sheet's "more like this" follows the provider.

## F. Mornye / SFLX addons

**F1. Signed-session host does not exist in Kotlin**
- The Rust reference (Mornye) is authoritative: bootstrap → challenge →
  exchange → refresh, ZARZ-HMAC-V1 signing, session records on disk.
- Deliverable: `SflxSignedSession.kt` + `SflxShim` bridge + a `sessionCall`
  native binding in `QuickJsExecutor` (module-scoped).
- JS surface the extension expects (from the Mornye prelude):
  `session.status()`, `session.clear()`, `session.completeGrant(grant)`,
  `session.signedFetch(method, path, body, headers)`; the last returns
  `{ok, error, statusCode, body, headers, needsVerification, code, retryable,
  retryAfterMs, retryMode}`.

**F2. No in-app verification browser**
- Symptom: an addon that needs a captcha cannot be completed at all.
- Fix: an in-app WebView popup that opens the challenge URL, intercepts
  `scheme://session-grant?grant=…&state=…`, calls `completeGrant(grant)`, and
  retries the extension call.
- State must match; `cb_version=v2grant`; the callback may be nested in `cb`.

**F3. Extension download result is thrown away**
- Symptom: hi-res / lossless / Atmos cannot be labelled — the codec, bit
  depth, sample rate and actual extension never reach the app.
- Cause: `file.download` throws to capture the URL, losing the result.
- Fix: keep the result, read `audio_codec`, `bit_depth`, `sample_rate`,
  `actual_extension`.

**F4. Quality tiers are not mapped from the manifest**
- Mornye's rule: `qualityOptions[].kind` ∈ {lossless, lossy, spatial};
  a request's kind decides the target — `lossless` may land on Hi-Res, but
  never on Atmos; `spatial` may fall back to lossless; a lossless request
  must not get spatial.
- Fix in Auris: map app tiers to the extension's options by kind, and label
  the result from the real codec.
- Rule from the user: "Lossless means up to Hi-Res, not atmos"; the Dolby rung
  must exist in download quality (already added in 3.0.27).

**F5. Segmented playback is unsupported**
- `file.downloadSegments` (Tidal / SoundCloud) has no transport in Auris.
- Fix: `SourceStream` carries transport + segments, MIME declared before the
  media source is built, cache policy stops treating a manifest as one
  contiguous file, read-ahead understands segments.

**F6. Extension scope**
- Sources-only (streaming/downloading), on/off toggle + priority, install by
  link, no bundled extensions. Keep it that way.

## I. A found upgrade is thrown away  ← LIVE BUG

**I1. Dolby Atmos upgrade found, fetched, then discarded** — FIXED (3.0.28)
- Symptom (user report): a track playing from YouTube is found again in a
  playlist at Dolby Atmos and never gets it. Log:
  `upgrade found: 'What About Jane' at Dolby Atmos` →
  `upgrade for CaiqWrL0zEE never proved itself in 25336ms` →
  `discarded unused rendition CaiqWrL0zEE#hifi`.
- Cause: the audition's proof was one arithmetic condition — "buffered through
  twelve seconds past the listener **and** a megabyte loaded". Both halves
  describe a progressive file. A Dolby Atmos addon hands over a **DASH
  manifest**: the index is a few kilobytes (so a megabyte is never loaded),
  its audio arrives as segments under their own cache keys, and it often
  states no length at all (so the duration check had nothing to compare).
  The upgrade was therefore proved, buffered, decoded — and refused for
  failing a condition written for a different container.
- Fix:
  - The proof is now a set of independent ways to be right: the full window
    with a megabyte behind it; the full window from a manifest (its
    buffered position *is* the evidence, since it was made of the segments);
    the bytes on disk reaching the listener even when the window is short;
    and a late proof after twelve seconds on a quarter-megabyte floor.
  - A source that states no length is no longer treated as a short one, in
    the audition *or* in the post-swap check (`watchUpgrade`): a check that
    reverts on what it cannot measure threw away the upgrade it was meant to
    protect.
  - The audition says what it is waiting for, once a second, and says what
    proved it. The old timeout named neither.
- Verify: a track found at Dolby Atmos swaps over instead of timing out; the
  log shows `upgrade proved: …` and `upgraded to Dolby Atmos at …ms`.

## J. SFLX signed sessions and verification — what landed in draft 2

**F1 — signed session host: DONE.** `data/sources/mornye/SflxSignedSession.kt`
is the whole protocol, ported line for line from Mornye's Rust:
- manifest `signedSession` defaults (`ext-1.0`, `extension`,
  `mornye://session-grant`, `SPOTIFLAC-HMAC-V1`, `X-Sig-`, `/bootstrap`,
  `/challenge`, `/session/exchange`, 300 s window);
- record at `<filesDir>/signed_sessions/<namespace>-<sha256(scope)[..16]>.json`,
  `install_id` = 16 random bytes hex, the record cleared when the scope
  changes;
- bootstrap `GET <base><bootstrap>?app_version=&install_id=`, retried once;
- challenge `?id=<challenge>&cb=<callback?cb_version=v2grant&state=<state>>`,
  32 random bytes base64url-no-pad for the state, 180 s lifetime;
- exchange `POST <base><exchange>` `{grant, install_id, app_version,
  platform}`, 429 retried up to three times with Retry-After clamped 1–300 s;
- refresh `POST <refresh>` `{install_id}` when the record expires within an
  hour and a refresh endpoint is declared;
- signing: UTC `%04d-%02d-%02dT%02d:%02d:%02d.%03dZ`, window =
  `unixSeconds / timeWindowSeconds`, rolling key =
  `HMAC-SHA256(secret, "<window>:<sessionId>")`, signature =
  base64url-no-pad `HMAC-SHA256(rollingKey, signingString)` over ten lines
  (scheme, method, escaped path, blank, body hash, timestamp, nonce, session
  id, app version, platform), body hash = lower hex SHA-256;
- error contract: 401/gateway/SESSION_INVALID/bootstrap_session → bootstrap;
  428/gateway/VERIFY_REQUIRED/verify → block this generation and surface the
  URL; 403/gateway/REQUEST_AUTH_INVALID → retry once on a newer session;
  503/provider/PROVIDER_UNAVAILABLE + retryable + same_operation → retry with
  Retry-After, twice.

`QuickJsExecutor` gained a synchronous, module-scoped
`__spine.sessionCall(method, argsJson)` plus `md5`/`sha256`/`hmacSHA256`/
`hmacSHA256Base64` (Mornye's argument order: message first, key second).
`SflxShim`'s `session.*` now calls the host and falls back to the old
"not implemented" answer only when the manifest declares no `signedSession`.

**F2 — verification browser: DONE.** `SflxVerifyActivity` is a
`Theme.BitChord.Verify` dialog hosting a WebView with third-party cookies.
It is opened from the host's application context, so it works from a download
as well as from the settings sheet. A non-`http(s)` callback carrying `grant`
is taken, `state` is checked against the challenge this host issued, and
`completeGrant` redeems it. The signed call that asked for it **waits** (up to
180 s) and retries itself, so the song starts when the captcha is solved
rather than needing a second press of play. `needsVerification`,
`open_auth_url` and `auth_url` are on every refusal, as in Mornye.

**F3 — download metadata: PARTLY.** The host still does not download, so the
real file's `audio_codec`/`bit_depth`/`sample_rate` (which Mornye only learns
after the bytes are on disk) cannot be read. What is captured now: the path
the extension was about to write, and its download options. Container from the
path's extension, codec from an option when stated, bit depth / sample rate /
bitrate from options when stated, and `audioModes: ["atmos"]` when the request
was immersive or the container is E-AC-3/AC-4. All of it lands in
`ModuleStreamTrack` and flows through the existing format handling.

**F4 — quality tiers: DONE.** `SflxQuality` now ports Mornye's rule:
`qualityOptions[].kind` ∈ {lossless, lossy, spatial}, inferred from id/label
when absent; lossless requests get lossless only, spatial may fall back to
lossless, lossy may fall back to lossless, never the other way. The Atmos
request reaches it because `ModuleSource` passes `request.wantsAtmos` and the
extension context now carries `dolbyAtmos`.

**F5 — segmented playback: NOT YET.** `file.downloadSegments` is still refused
out loud.

**Status in the UI: DONE.** Each extension whose manifest declares a
`signedSession` shows a badge under its name — "Verified · until …", "Needs
verification — open the addon to verify", or the failure — and its settings
sheet has a Sign-in block with **Verify** and **Forget**. The state is read
into `SflxCatalog.statuses` and refreshed on install, removal, grant and
settings save, so the list is not doing file I/O on every recomposition.
