## A. Player transport (reported: play/pause too big)

**A1. The play button was twice its size.** — FIXED
- Cause: the transport was copied out at 74dp (58dp compact) while the skip
  glyphs kept BitChord's own 53dp, so the play button dominated the row.
- Fix: the play glyph is back at 38dp (30dp compact). Everything else about the
  row is untouched: 53dp skips, their 0.85 height squash, SpaceAround spacing,
  and the 92dp/76dp touch boxes.
- Verify: transport row height against the 3.0.28 reference screenshot.

**A2. Bottom row had its own idea of a dim glyph.** — FIXED
- Cause: `BOTTOM_GLYPH_REST_ALPHA = 0.75f`, a second opacity scale beside the
  main player's role-based alphas.
- Fix: an unlit bottom glyph is `alphas.tertiary` (0.65), the same role that
  draws lyrics, queue and AirPlay. One scale, named once.

## B. Spotify catalogue

**B1. Search returned nothing, with no error.** — FIXED (3.0.29)
- Rows no longer require a match to appear; `spotify:<id>` rows are playable.

**B2. Search followed the wrong operation set.** — FIXED
- Search now asks the web player's own tab operations in order —
  `searchTracks`, `searchAlbums`, `searchArtists`, `searchPlaylists` — with
  myspoti's variable set, and reads myspoti's response paths
  (`searchV2.tracksV2/albumsV2/artists/playlists`, `topResultsV2`).
- The entity is walked out of the entry at whatever depth the answer wraps it,
  and `pagingInfo.nextOffset` drives paging.
- Empty answers name the key set they carried, so the next build's answer is
  read rather than guessed at.
- Tests: `SpotifySearchTest` gains the myspoti shapes (2 new cases).

**B3. Playlist rows greyed out and unclickable.** — FIXED
- Cause: a track that no source matched was written as `sp-miss:<id>`, which
  the shared row draws as unavailable and `playFrom` refuses.
- Fix: the row is the Spotify catalogue row (`SpotifyHomeSource.songFor`), with
  the id `spotify:<id>`; the player asks the enabled sources for the recording
  by name when the row is reached. No YouTube dependency.
- The `sp-miss:` handling in `Common.kt` stays on purpose: a queue snapshot
  saved by 3.0.29 can still carry one of those rows, and it must keep reading as
  unavailable rather than turning into a row that cannot play.
- Verify: a Spotify playlist whose tracks the matcher missed is playable.

**B4. Queue rows drew a LOSSLESS chip.** — REMOVED
- The chip is gone from `ExplicitSongTitle` and from every caller
  (`PlayerQueue`, `PlayerQueueSearch`, `DetailScreen`). The player's own
  quality badge — the thing that reports what is *actually* being served — is
  untouched.

**B5. Radio on the Spotify catalogue played the liked list.** — FIXED
- Cause, two halves:
  1. `SpotifyAlgorithm.station` needs the Spotify id behind the seed, kept in
     `SpotifyHomeSource.spotifyIds`. Playlist and collection rows are matched
     through `SpotifyImporter` directly, which never filled that map, so the
     station was never asked for. A restored queue lost the map entirely.
  2. When the algorithm answered nothing, `autoplayTracks` fell back to
     `flowSeeds()` — which prefers **Liked Songs** on purpose — so the radio
     became a shuffle of the library.
- Fix:
  - `rememberSpotifyId` is called on every path that turns a Spotify track into
    a row or a match, including the page matcher.
  - `spotifyIdOf` also recovers the id from a `spotify:<id>` row, so a queue
    restored from disk still knows what to ask about.
  - The station answer is `SpotifyAlgorithm.more` (station, then Spotify's
    artist graph). An explicit station that gets neither now says so and stays
    empty instead of becoming the liked list.
  - A queue top-up that gets neither falls back to the *catalogue* — top
    tracks, then recently played, then the public lists — never the liked list.
  - The unknown-seed case is logged ("no Spotify id behind it"), because from a
    log it is otherwise indistinguishable from Spotify answering with nothing.

## C. Local songs

**C1. A downloaded song could never be upgraded.** — FIXED (3.0.29)
- `adoptFileBackedTrack` offers the sources over the file, gated by the
  listener's own switch. Confirmed working on device.

**C2. The next track was never prepared when it was a download.** — FIXED
- Cause: read-ahead drops every id in `Downloads.saved` — correct for bytes
  (the file is on disk and plays as itself), wrong for the *search*: nothing
  looked for a better copy of a saved song until it was already playing, which
  is the one moment the listener waits.
- Fix: `AudioCache.prepareDownloadedHead` runs the same
  `SourceResolver.prepareForPlayback` that the streamed read-ahead uses, for the
  next track when it is a download, and warms nothing. Gated exactly like the
  live local search: the listener's switch (`effectiveAutoUpgradeLocalStorage`,
  so offline turns it off) and a source that can serve lossless.
- Verify: queue of saved songs → the next one has its better copy found before
  it starts.

## D. Parked (named, not fixed)

**D1. Locally upgraded songs are not analysed by Automix.** — PARKED, needs one
device log.
- Known pieces: a local file is analysed down the `LocalAudioSource` path
  (`TrackAnalyzer.copyToRead` short-circuits the cache for local URIs), and the
  post-upgrade head warm (`AudioCache.warmRange(upgradedUri, …)`) is a no-op for
  `file://`/`content://` because the cache is keyed from the URI and local URIs
  are routed past it. Which of the two leaves the upgraded copy unanalysed
  cannot be told from code alone.
- Next step: one device run with `BCFetchDebug` + `TrackAnalyzer` logging while
  a local track upgrades and the next transition is planned.

**D2. The colour engine does not reach the lyrics panel.** — PARKED LAST.
- Symptom: translate, romanize, Sing and "Lyrics by …" buttons keep their own
  colours, and the lyrics text itself follows the album colour only sometimes.
- Engine: `LocalPlayerAccent` (`PlayerColorCustomization.kt`), provided once at
  `NowPlayingScreen.kt`; the transport and most of the player read it.
- Not reading it: the lyric controls and labels in `PlayerLyrics.kt` (translate
  ~1296, romanize ~1347, "Lyrics by" ~2990) and parts of the lyrics text.
- Requested last, after everything above.
